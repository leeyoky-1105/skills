# Spec Traceability Skill — 引导式需求追踪矩阵助手

## Skill 元信息

| 属性 | 值 |
|:---|:---|
| **名称** | `spec-traceability` |
| **版本** | 1.0.0 |
| **类型** | 人机协作 Skill |
| **配套文档** | 《需求追踪矩阵》（14 模块） |

---

## 触发条件

当用户提出以下请求时使用此 Skill：

- "帮我写追踪矩阵"
- "建立需求追溯"
- "检查覆盖率"
- "RTM 怎么做"
- "需求全链路追溯"

---

## 核心理念

> **14 只做一件事：建立需求（REQ）↔ 用户故事（UserStory）↔ API 端点 ↔ 测试用例（TC）的四向追溯链路。变更需求时，沿链路定位受影响的用户故事、API、测试用例。**
>
> AI 负责引导提问和结构化整理，人负责提供真实的追溯关系。

## Step 1: 确认输入来源

### AI 操作

1. 检查是否已有 `05-用户故事`、`09-API规格`、`13-测试策略` 的输出
2. 确认需要追溯的需求范围

---

## Step 2: 需求编号体系（§1）

### AI 操作

确认编号格式与 01 总则一致：

```markdown
📋 需求编号体系

| 编号格式 | 含义 | 示例 |
|----------|------|------|
| REQ-{模块号}-{NNN} | 功能需求 | REQ-M1-001 |
| RULE-{NNN} | 数据/类型约束规则 | RULE-001 |

| 级别 | 含义 | 门禁影响 |
|------|------|----------|
| P0 | 必须实现，阻塞发布 | 关联测试用例全绿方可合并 |
| P1 | 应当实现，不阻塞首版 | CI warning |
| P2 | 可选增强 | 不纳入门禁 |
```

---

## Step 3: 需求定义表（§2）

### 🛑 AI 不臆造需求

```markdown
🛑 需求列表必须从 05/09 中提取，AI 不臆造。

| 需求编号 | 需求名称 | 优先级 | 来源 | 详细说明 |
|----------|----------|--------|------|----------|
| REQ-M1-001 | {需求名称} | P0 | 05 US-001 | {详细说明} |
| REQ-M1-002 | {需求名称} | P0 | 09 §X | {详细说明} |
| RULE-001 | {约束描述} | P0 | 09 DTO | {约束说明} |
```

---

## Step 4: 正向追溯矩阵（§3）

### AI 操作

建立 REQ → US → API → TC 链路：

```markdown
📋 正向追溯矩阵

阅读方向：需求 → 用户故事 → API 端点 → 测试用例

| 需求编号 | 用户故事/AC来源 | API 端点 | 测试用例编号 | 覆盖状态 |
|----------|-----------------|----------|-------------|----------|
| REQ-M1-001 | {US-001} | {API端点} | {TC编号} | ✅/❌ |
| REQ-M1-002 | {US-002} | {API端点} | {TC编号} | ✅/❌ |

⚠️ 请确认：
☐ 每条 REQ 是否都有对应的 US？
☐ 每条 REQ 是否都有对应的 API？
☐ 每条 REQ 是否都有对应的 TC？
☐ 是否有覆盖状态为 ❌ 的？
```

---

## Step 5: 反向追溯矩阵（§4）

### AI 操作

建立 TC → REQ 反向链路：

```markdown
📋 反向追溯矩阵

阅读方向：每条测试用例追溯回需求。测试失败时定位哪条需求受影响。

| 测试用例编号 | 测试层级 | 关联需求 | 断言要点 |
|-------------|----------|----------|----------|
| TC-M1-001 | {层级} | {关联需求} | {断言要点} |
| TC-M1-002 | {层级} | {关联需求} | {断言要点} |
```

---

## Step 6: API → TC 映射（§5）

### AI 操作

建立 API 端点与测试的映射：

```markdown
📋 API → TC 映射

确保每个 API 端点至少有 1 条测试覆盖。

| # | API 端点 | 方法 | 关联TC编号 | 覆盖状态 |
|---|----------|------|-----------|----------|
| 1 | {端点1} | {方法} | {TC编号} | ✅/❌ |
| 2 | {端点2} | {方法} | {TC编号} | ✅/❌ |
```

---

## Step 7: 覆盖率分析（§6）

### AI 操作

统计各维度覆盖率：

```markdown
📋 覆盖率分析

| 维度 | 已覆盖 | 总数 | 覆盖率 |
|------|--------|------|--------|
| API 端点 | {已覆盖} | {总数} | {百分比} |
| REQ 需求条目 | {已覆盖} | {总数} | {百分比} |
| TC 测试用例 | {已统计} | {目标总数} | {百分比} |

### 关键风险

| 风险项 | 严重度 | 说明 |
|--------|--------|------|
| {如：某模块零测试} | {严重度} | {说明} |

⚠️ 请确认：
☐ 覆盖率是否达标？（通常 P0 需求 100% 覆盖）
☐ 关键风险是否有应对计划？
```

---

## Step 8: 输出追踪矩阵文档

### AI 操作

汇总所有内容，输出完整的 `14-需求追踪矩阵` 文档。

---

## 关键行为准则

### AI 可以做

| ✅ 可以做 | 说明 |
|:---|:---|
| 从 05/09/13 提取数据 | 格式化整理 |
| 建立追溯关系 | 基于已有文档 |
| 统计覆盖率 | 自动化计算 |
| 识别覆盖缺口 | 标记 ❌ 项 |

### AI 绝不可以做

| 🛑 绝不可以 | 原因 |
|:---|:---|
| 臆造需求列表 | 需从 05/09 提取 |
| 臆造追溯关系 | 需与各文档对齐 |
| 自行判定覆盖率达标 | 需 QA 确认 |
| 臆造测试用例 | 需与 13 对齐 |
