## 触发条件

当用户提出以下请求时使用此 Skill：

- "帮我写测试策略"

- "质量门禁怎么设"
- "TC 怎么拆"
- "测试分层怎么做"

---

## 核心理念

> **13 只做一件事：定义测试策略和质量门禁。核心理念是"数可独立失败的点"——每条 TC 只回答一个问题，失败时不看代码就知道哪里坏了。**
>
> AI 负责引导提问和结构化整理，人负责提供真实的测试用例和门禁条件。

## Step 1: 确认输入来源

### AI 操作

1. 检查是否已有 `05-用户故事`、`09-API规格`、`12-实施计划` 的输出
2. 确认需要定义的测试范围

---

## Step 2: 测试分层（§1）

### AI 操作

引导定义 4 层测试：

```markdown
📋 测试分层

共 4 层，写测试前先搞清楚每层验什么。

| 层级 | 工具 | 覆盖对象 | 说明 |
|------|------|----------|------|
| L1 Unit | {pytest/JUnit} | 单个函数/类的逻辑 | 不依赖网络，最快 |
| L2 Integration | {测试工具} | API 端点 + 存储 | 模拟 HTTP 请求 |
| L3 Contract | {测试工具} | 响应体结构与 09 一致 | 验字段名、类型 |
| L4 E2E | {测试工具} | 完整用户旅程 | 浏览器级操作 |
```

---

## Step 3: 用例拆分原则（§2）

### AI 操作

解释"数可独立失败的点"原则：

```markdown
📋 用例拆分原则

核心理念：每条 TC 只回答一个问题，失败时不看代码就知道哪里坏了。

| 来源 | 计数方法 | 示例 |
|------|----------|------|
| 正常路径 | 每个端点的 happy path = 1 条 | 核心接口请求成功 → TC-001 |
| 错误码 | 每个 distinct error code = 1 条 | EMPTY_QUERY = TC-002 |
| 分支路径 | 每个 if/else 降级分支 = 1 条 | 无 API Key → demo = TC-004 |
| 类型约束 | Spec 09 约定的字段类型 = 1 条 | llm_used 必须 bool = TC-006 |
```

```markdown
| TC-ID | 层级 | 覆盖方法 | 断言要点 | 优先级 |
|-------|------|----------|----------|--------|
| TC-M1-040 | Unit | {Storage方法} | {断言要点} | P0 |
```

## Step 5: 质量门禁（§4）

```markdown
📋 质量门禁

| Gate-ID | 条件 | 阻塞合并 |
|---------|------|----------|
| G-LINT | {lint命令}通过 | 是 |
| G-UNIT | Unit 测试全绿 | 是 |
| G-INT | Integration 测试全绿 | 是 |
| G-AC | P0 验收标准全覆盖 | 是 |
| G-PERF | response_time_ms < 5000 | 否（warning） |

### 执行命令

cd {后端目录}
{测试运行命令}
```

## Step 6: TDD 适用场景（§5）

### AI 操作

分析各场景的 TDD 价值：

```markdown
📋 TDD 适用场景

| 场景 | TDD 价值 | 建议 |
|------|----------|------|
| 简单 CRUD | 低 | 写完补测试 |
| 参数校验 / 错误码 | 中 | 建议 TDD |
| 多级降级 / 状态机 | 高 | 强烈建议 TDD |
| 复杂业务计算 | 极高 | 必须 TDD |
```

## 关键行为准则

### AI 可以做

| ✅ 可以做 | 说明 |
|:---|:---|
| 解释测试分层 | 标准化知识 |
| 建议 TC 拆分 | 供用户确认 |
| 分析 TDD 价值 | 供用户决策 |
| 建立追溯关系 | 格式化整理 |

### AI 绝不可以做

| 🛑 绝不可以 | 原因 |
|:---|:---|
| 臆造测试用例 | 需 QA 确认 |
| 自行定义门禁条件 | 需团队确认 |
| 臆造断言要点 | 需与 09 对齐 |
| 自行判定测试覆盖 | 需 QA 确认 |
