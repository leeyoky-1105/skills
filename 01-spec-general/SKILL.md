## 触发条件

当用户提出以下请求时使用此 Skill：

- "帮我建立 Spec 文档体系"
- "初始化 Spec 编号规范"
- "Spec 写作规则是什么？"
- "14 个 Spec 文档分别是什么？"
- "怎么组织 Spec 文档结构？"

---

## 核心理念

> **Spec 文档体系是项目需求到实现的全链路真相来源。本文档定义写作规则、编号规范和阶段流程，是所有其他 Spec 文档的基础。**

## Step 1: 确认项目基本信息

### AI 操作

1. 收集项目名称和缩写
2. 确认模块编号规则（如 `M1-XXX`）
3. 确认团队成员角色（PM、TL、后端、前端、QA、DevOps）

### 👤 需要用户提供的信息

```markdown
在建立 Spec 文档体系之前，我需要了解以下信息：

1. 项目名称和缩写是什么？（如：安踏OMS → ANTA）
2. 模块编号规则是什么？（如：M1-001, M2-001）
3. 团队中有哪些角色？
   - PM（产品负责人）
   - TL（技术负责人）
   - 后端开发
   - 前端开发
   - QA
   - DevOps
4. 文档存储位置在哪里？（如：Git 仓库 docs/spec/ 目录）
```

## Step 2: 初始化 14 模块文档结构

### AI 操作

根据编号与阶段对照表，创建 14 个文档的框架：

| 编号 | 阶段 | 分类 | 文档名称 |
|:---|:---|:---|:---|
| `01` | Meta | 总则 + 编号 | Spec 写作规则、RFC 规范词、编号命名 |
| `02` | Meta | Elicitation | 需求来源与采集记录 |
| `03` | Proposal | Proposal | 立项提案与范围说明 |
| `04` | Proposal | PRD | 产品需求说明 |
| `05` | Spec | UserStory | 用户故事与验收标准 |
| `06` | Spec | FSD | 功能规格说明 |
| `07` | Spec | NFR | 非功能需求与约束 |
| `08` | Design | Architecture | 系统架构与技术选型 |
| `09` | Design | API | 接口规格（契约真源） |
| `10` | Design | Data | 数据模型与存储规格 |
| `11` | Design | Security | 安全设计规格 |
| `12` | Plan | Plan | 实施计划与里程碑 |
| `13` | Test | Test | 测试策略与质量门禁 |
| `14` | Trace | Traceability | 需求追踪矩阵（四向对齐） |

### AI 输出

为每个文档生成元数据头部：

```markdown
| 项 | 值 |
|---|---|
| 模块编号 | {项目缩写}-M{序号} |
| 模块名称 | {模块名称} |
| 文档版本 | v0.1 |
| 文档状态 | Draft |
```

## Step 3: 建立统一编号规范

### AI 操作

根据用户提供的项目信息，生成统一编号模板：

| 对象 | 格式 | 示例 |
|:---|:---|:---|
| 需求编号 | `REQ-{模块号}-{NNN}` | REQ-M1-001 |
| 用户故事 | `US-{NNN}` | US-001 |
| 验收标准 | `AC-{US编号}-{NN}` | AC-001-01 |
| 测试用例 | `TC-{模块号}-{NNN}` | TC-M1-001 |
| 规则约束 | `RULE-{NNN}` | RULE-001 |

### 👤 确认点

```markdown
⚠️ 请确认：
☐ 编号格式是否符合团队习惯？
☐ 是否需要增加其他编号类型？（如 API 编号、数据表编号）
☐ 编号中的模块号前缀是否已确定？
```

---

## Step 4: 确认 RFC 规范词和写作约束

### AI 操作

展示 RFC 风格规范词定义：

| 词 | 含义 |
|:---|:---|
| **MUST** | 必须，违反即缺陷 |
| **SHOULD** | 建议，不满足需说明理由 |
| **MAY** | 可选，不影响基线验收 |
| **MUST NOT** | 严禁 |

### 写作约束清单

- 时间统一 `ISO-8601 UTC`
- 所有 API 字段名一律在 `09` 冻结，其他文档只引用不另起别名
- 所有业务规则必须关联 `REQ-ID`、`UserStory-ID`
- 所有 AC 必须可映射到 `TC-ID`
- 所有跨模块依赖必须写明「依赖类型 / 影响范围 / 回退策略」

---

## Step 5: 确认六阶段流程和写作顺序

### 六阶段流程

```
Proposal(03-04) → Spec(05-06-07) → Design(08-09-10-11) → Plan(12) → Test(13) → Trace(14)
  Why              What              How             When/Who     OK?      All linked?
```

| 阶段 | 编号 | 完整问题 | 产出物 |
|:---|:---|:---|:---|
| **Proposal** | 03 + 04 | 为什么要做？做什么不做什么？ | 立项提案 + PRD |
| **Spec** | 05 + 06 + 07 | 用户要什么？功能什么样？约束底线？ | 用户故事 + FSD + NFR |
| **Design** | 08 + 09 + 10 + 11 | 怎么架构？接口契约？数据怎么存？ | 架构 + API + 数据模型 + 安全 |
| **Plan** | 12 | 什么时候交付？谁来做？ | 里程碑 + WBS |
| **Test** | 13 | 做对了没？门禁是什么？ | TC + 质量门禁 |
| **Trace** | 14 | 全对得上吗？有没有漏？ | 四向追溯矩阵 |

### 写作顺序（四轮螺旋推进）

| 轮次 | 文档 | 做什么 | 清晰度 |
|:---|:---|:---|:---|
| **1. 起点** | 03 → 04 | 提炼原始素材 → 立项 → 产品需求 | 30% |
| **2. 锚定** | 05 + 09 | 用户故事与 API 接口互相校准 | 60% |
| **3. 展开** | 08 + 10 → 06 + 07 | 架构+数据展开；06/07 被倒逼补全 | 85% |
| **4. 收口** | 12 + 13 → 14 | 计划+测试并行；14 终检全链路 | 95% |

## 关键行为准则

### AI 可以做

| ✅ 可以做 | 说明 |
|:---|:---|
| 创建 14 模块文档框架 | 按模板生成结构 |
| 生成编号规范 | 基于用户提供的规则 |
| 展示写作约束和流程 | 标准化内容 |
| 生成术语表 | RFC 规范词 + 缩写表 |

### AI 绝不可以做

| 🛑 绝不可以 | 原因 |
|:---|:---|
| 自行填写业务内容 | 不了解项目业务 |
| 自行决定模块编号 | 需团队统一约定 |
| 自行设定文档状态为 Approved | 需人工审核签字 |
